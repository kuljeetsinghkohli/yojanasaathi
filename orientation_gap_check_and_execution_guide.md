## Part 1 — Gap Check: What We Need to Fold In

Going back through Week 1–4 against what's already built (one-pager, 16-scheme dataset, matching prompt), five things stood out that the current plan doesn't yet cover explicitly.

**1. The "Responsible AI Principles for the Hackathon" (Week 2) aren't in the one-pager yet.** This was a named slide, not general advice, so judges may specifically look for it. The six asks and how YojanaSaathi should meet each one:

- *Use anonymized data* — never put a real farmer's name, phone number, or Aadhaar-linked detail into a demo or a screenshot. Build 3–5 fictional test profiles (e.g., "Ramesh, marginal farmer, MP, rain-fed") and use only those, in the app and in any slides.
- *Test for bias* — check that the matcher gives sensible results across different states, languages (Hindi vs. English input), landholding sizes, and farmer categories — not just the one profile you like best. This is also just good QA.
- *Disclose AI use* — say plainly, in the app UI and in your pitch, that scheme matching is done by an LLM. A one-line footer like "Matches are generated by AI based on the information you provide — please verify eligibility on the official portal before applying" does this and doubles as a hallucination safeguard.
- *Keep humans in the loop* — the app should recommend, not auto-apply. Make sure nothing in the UI implies the system submits an application or makes a final eligibility decision on the farmer's behalf.
- *Secure your API keys* — if you push code to GitHub (likely, since Bob's flow clones/works from a repo), put your LLM API key in a `.env` file and add `.env` to `.gitignore` from the very first commit. A leaked key in a public repo is an easy, avoidable deduction.
- *Verify outputs* — before demo day, manually check the scheme names, benefit amounts, and eligibility rules the matcher returns against the official links in the dataset. This is also called out in the matching-prompt guardrails already, so it's just a matter of actually doing the pass.

## Part 2 — Quick Reference: Key Observations by Session

**Week 1 — How to Think Like an AI Solution Builder**
AI-first mindset: Observe → Identify Problem → Understand Users → "Can AI help?" checklist. GenAI capabilities and limits (hallucinates, confidently wrong, misses recent events, reflects training bias, misreads vague prompts). Bob intro: four modes — **Plan** (think before code), **Code** (implement), **Ask** (explain/discuss), **Orchestrate** (multi-step complex runs).

**Week 2 — Building Responsible AI Solutions**
Five pillars: Privacy, Fairness, Security, Human Oversight, Transparency. You are always the decision-maker — verify before trusting, disclose AI use, don't outsource judgment. Bias enters through data collection, labeling, feature selection, training, and feedback loops. Strong-prompt anatomy: Role, Task, Context, Constraints, Format. Never put real passwords, health records, banking details, or national ID data into an AI tool. The six Hackathon Responsible-AI asks are listed in Part 1 above.

**Week 3 — Building with IBM Bob**
Install flow: bob.ibm.com → 40 free Bobcoins over 30 days → install → OAuth login → clone repo → open in Bob. Problem-understanding framework: Users / Challenges / Objectives / Scope. Project-planning framework: Roadmap → Milestones → Workflows → Responsibilities. Best practices: be specific, always review generated code, iterate progressively, never share confidential data, human judgment stays essential. The Iterative Prompting Workflow: idea → ask Bob for approaches → generate initial implementation → refine via follow-ups → improve from testing/feedback. This is the same shape as the bob_prompts.txt example (analyze → plan → critique plan → implement → test → debug → final review) — that's your template for literally every Bob session.

**Week 4 — Transforming Ideas into Impactful Solutions**
Solution design: Identify Users & Objectives → Break Into Components → Design for Scale → Scope Features ruthlessly (essential vs. nice-to-have — cut hard, given 5 days). Workflow design: map the end-to-end user journey and data flow before coding. Demo flow: Introduction → Solution Walkthrough → Live Demo → Impact Statement; avoid unclear benefits and rushed pacing; rehearse out loud more than once. Judging criteria and evaluator red flags/green flags are in Part 1.

## Part 3 — Step-by-Step Execution Guide (Aug 27 → Aug 31)

You're new to this, so each day below says what to do, which Bob mode to use, and roughly what "done" looks like. Treat the bob_prompts.txt pattern as your default rhythm inside Bob: **ask it to analyze and plan first, review that plan yourself (or ask Bob to critique it), then implement — don't jump straight to "write me the code."**

### Day 1 (Aug 27) — Setup + Plan Mode
1. If you haven't already, install Bob from bob.ibm.com, sign in, and connect it to a fresh GitHub repo (private repo is fine — remember `.env` + `.gitignore` from commit #1).
2. Upload the three deliverables already built — the one-pager, `farmer_schemes_dataset.json`, and `scheme_matching_prompt.md` — into the repo or paste their contents into Bob's context.
3. In **Plan mode**, prompt Bob roughly like this: *"Analyze this problem statement and dataset. Do not write code yet. Identify: users, functional requirements, required components, data flow from farmer input to scheme match to display, and any ambiguities. Then propose a simple architecture (frontend + backend + LLM call) sized for a 4-day solo build."*
4. Read Bob's plan critically — this is the "critique as a senior architect" step from the pattern. Cut anything not essential (no database needed; no auth needed; no need to support more than the 16 schemes for MVP).
5. **Done when:** you have an approved, written-down architecture and a repo skeleton (folders, no real code yet).

### Day 2 (Aug 28) — Code Mode: Backend
1. In **Code mode**, ask Bob to implement the backend: load the scheme dataset, accept a farmer profile (the 6 fields from the prompt template), call the LLM with the system prompt from `scheme_matching_prompt.md`, and return the parsed JSON matches.
2. Explicitly tell Bob: *"Keep business logic independent of the UI. Validate malformed profile input. Handle the case where the LLM returns invalid JSON."*
3. Ask for basic tests (2–3 fixed farmer profiles, checking the response shape).
4. Use **Ask mode** for any concept you don't follow in what Bob generated — this is the point of that mode, don't skip explanations you don't understand.
5. **Done when:** you can run one farmer profile through the backend from a terminal/script and get sensible matches back.

### Day 3 (Aug 29) — Code Mode: Frontend
1. Ask Bob (Code mode) for a simple form: the 6 input fields, a submit button, and a results view that renders `scheme_name`, `why_you_qualify`, `what_you_get`, `next_step`, and `confidence` per match, plus the `notes_for_farmer` line when present.
2. Make sure the UI can render Hindi text correctly (the prompt template's example responds in Hindi when the farmer writes in Hindi).
3. Add the disclosure footer from Part 1 ("Matches are generated by AI... verify on the official portal").
4. **Done when:** you can fill the form in the browser and see real matches rendered, in both an English-input and a Hindi-input test.

### Day 4 (Aug 30) — QA + Responsible AI Pass
1. Build the small test matrix (QA-engineer style, per bob_prompts.txt): try 4–5 synthetic profiles spanning different states, farmer categories, irrigation types, and one landless/non-farming profile to see the "no strong match, here's who to contact" path actually fires.
2. This is your bias check from Part 1 — look specifically for any profile type getting oddly poor or empty results.
3. Manually verify 3–4 of the scheme facts you'll say out loud in the demo (subsidy %, rupee amounts) against the official links in the dataset.
4. Confirm `.env`/API key isn't committed anywhere in the repo history.
5. Polish rough UI edges; add friendly error messages for empty/invalid input.
6. **Done when:** the app handles your test matrix cleanly and you've double-checked the numbers you'll quote.

### Day 5 (Aug 31) — Demo Prep + Submission
1. In **Orchestrate mode**, ask Bob for a final holistic review across the whole codebase (architecture, error handling, code quality, anything you'd fix with one more day) — you don't have to fix everything, but note it, since "what would you improve" is a great answer if a judge asks.
2. Write a short README that states plainly: the problem, the solution, how Bob was used at each stage (plan/code/ask/orchestrate), and the responsible-AI steps taken. This doubles as your "Team Collaboration" answer from Part 1.
3. Script the demo using the Week 4 structure: **Introduction** (a farmer facing scheme confusion) → **Solution Walkthrough** (show the architecture briefly) → **Live Demo** (run 1–2 of your synthetic profiles live, one in Hindi) → **Impact Statement** (e.g., "16 real central schemes covered, a 5-minute conversation instead of a trip to a government office").
4. Rehearse it out loud at least twice, with a timer.
5. Submit via the Zoho form (https://survey.zohopublic.in/zs/hLB5LB) well before the deadline — don't wait until the last hour in case of upload issues.
